# CLAUDE.md

Operating instructions for AI agents working in this repository.
Read this file, then `docs/domain-rules.md`, before proposing any change.

---

## What this project is

**TaskFlow** — a lightweight work-tracking API (a very small Jira). Backend only; there is no UI and none
is planned.

- **.NET 8**, C# 12, nullable reference types enabled.
- **PostgreSQL 16** via EF Core 8 + Npgsql. Runs locally in Docker.
- **API only.** Controller-based ASP.NET Core Web API.
- Built as a take-home exercise. Every non-obvious decision is written up, with alternatives and
  trade-offs, in `DECISIONS.md` (private — not part of the public repo; see below).

### The governing constraint

This codebase will be **read aloud and edited live under time pressure** by its author, in front of a
panel. Optimise for navigability and obviousness over cleverness. When two designs are equally correct,
choose the one that's easier to explain in one sentence.

Concretely: **do not add abstraction without a named, present problem it solves.** A layer that might be
useful later is a layer that has to be explained today.

## Repository layout

A **single project**, not a physical multi-project split — see `DECISIONS.md` #011 for why. The
dependency rule below is enforced by an architecture test, not the compiler.

```
TaskFlow.Api/
  Domain/
    Entities/                Project, WorkItem, Comment, User - the four entities. No EF Core, no
                              ASP.NET, no NuGet packages beyond the BCL. Private setters throughout;
                              state changes only through named methods (Transition(), AllocateNextNumber()).
    Exceptions/               Domain-thrown exceptions (InvalidTransitionException, NotFoundException, ...)
  Application/
    Services/                 One service per aggregate. Load, mutate via a domain method, SaveChangesAsync.
                               Services reference AppDbContext directly - no repository, no interface.
    DependencyInjection.cs     AddApplication()
  Infrastructure/
    Persistence/
      AppDbContext.cs
      Configurations/          One IEntityTypeConfiguration<T> per entity.
      Migrations/               Generated by `dotnet ef migrations add` - run by a human, never by an
                                agent. See "Commands" below.
    DependencyInjection.cs     AddInfrastructure()
  Contracts/                   Request/response DTOs (records) + hand-written *Mappings.ToDto() extensions.
  Controllers/                 Thin - bind, call service, map, return. No DbContext, no business logic.
  ExceptionHandling/           TaskFlowExceptionHandler - the one place exceptions become ProblemDetails.
  Program.cs                   All DI wiring, middleware pipeline.
tests/
  TaskFlow.UnitTests/          Domain entity tests. No database. Application services deliberately have
                                no unit tests - see DECISIONS.md #010.
  TaskFlow.IntegrationTests/   WebApplicationFactory + Testcontainers - real Postgres, one container per
                                test class.
docs/
  domain-rules.md              The specification. Code and tests answer to this file, not the reverse.
docker-compose.yml              Postgres 16 for local development.
DECISIONS.md                    Private decision log (gitignored) - not part of the public deliverable.
```

### Dependency direction

`Domain` references nothing. Everything else may reference `Domain`. `Application` and `Infrastructure`
may both touch `AppDbContext` directly (no repository — see `DECISIONS.md` #011). If a change would
require anything under `Domain/` to reference EF Core or ASP.NET, **stop and flag it.**

### Why `AddInfrastructure` reads the connection string lazily

Confirmed directly (temporary trace logging, since removed): a `WebApplicationFactory`-hosted test's
`ConfigureAppConfiguration` override is **not merged into configuration until `builder.Build()` runs.**
Reading `builder.Configuration.GetConnectionString(...)` at any point before `Build()` — no matter where
in `Program.cs` — sees the un-overridden value (`appsettings.json`'s real dev connection string, in this
app's case). Only `app.Configuration`, or anything resolved from the built `IServiceProvider` afterward,
reflects the override. This is a general fact about how `WebApplicationFactory` layers config onto a
minimal-hosting-model app, not something specific to this codebase.

`AddDbContext<AppDbContext>` uses the `(IServiceProvider, DbContextOptionsBuilder)` overload specifically
because of this: it resolves `IConfiguration` and reads the connection string **inside** the
options-building lambda, which EF Core invokes once per `AppDbContext` construction, long after `Build()`
has completed and the app is actually serving requests — not once, eagerly, at startup. An earlier eager
version (`configuration.GetConnectionString(...)` called directly, before `AddDbContext`) silently broke
`TaskFlowApiFactory`'s override for exactly the reason above: integration tests were quietly running
against the real local dev Postgres instead of an isolated Testcontainers instance, undetected, because
they still passed. Keep the connection string read lazy; don't move it back to a value captured once at
startup, before `Build()`.

## Commands

```bash
docker compose up -d                                   # Postgres on :5432
dotnet build                                           # must be warning-free
dotnet test                                            # unit + integration (needs Docker running)
dotnet run --project TaskFlow.Api                      # Swagger at /swagger

# migrations - run by the user, never by an agent (same reasoning as git commit/push: it's a
# permanent, generated artifact, and the human running the exercise should be the one who triggers it)
dotnet ef migrations add <Name> --project TaskFlow.Api --output-dir Infrastructure/Persistence/Migrations
dotnet ef database update --project TaskFlow.Api
```

## The vertical slice

Every feature follows the same path:

1. `Domain/Entities/` — entity change or new method. Business rules live here.
2. `Infrastructure/Persistence/Configurations/` — EF configuration for any new property.
3. Migration — generated by the human running `dotnet ef migrations add`, never by an agent.
4. `Application/Services/` — service method: load, call the domain method, `SaveChangesAsync`.
5. `Contracts/` — request/response DTOs (records) + a `*Mappings.ToDto()` extension.
6. `Controllers/` — thin action: bind, call service, map, return.
7. `tests/TaskFlow.UnitTests/` — only for `Domain/` changes; services get no unit tests (DECISIONS.md #010).
8. `tests/TaskFlow.IntegrationTests/` — for any new endpoint or new failure mode, through the real
   HTTP pipeline against a real (Testcontainers) Postgres.

## Hard rules

1. **Business rules live on the domain entity**, never in services, controllers, or validators. The
   status state machine (`WorkItem.Transition()`) and the hierarchy tier rule
   (`WorkItem`'s constructor, via `ValidateParent`) are the two examples. Never add a public setter for
   `Status` or a way to construct an illegal `ParentId`.
2. **No repository over `DbContext`.** `AppDbContext` is injected directly into services. See
   `DECISIONS.md` #011 for why this doesn't need an interface in a single-project layout.
3. **No MediatR, CQRS, AutoMapper, message broker, or caching layer**, and no Dapper (see `DECISIONS.md`
   #008 — EF Core only, on purpose).
4. **Controllers stay thin** — bind, call the service, map, return. No `DbContext`, no business logic, no
   try/catch (the exception handler owns error translation).
5. **No new NuGet dependency** without flagging it and stating what problem it solves.
6. **Cancellation tokens** flow from the controller action through the service to every EF call.
7. **Async all the way.** No `.Result`, no `.Wait()`, no `async void`.
8. **Never call `DateTime.UtcNow`.** Inject `TimeProvider`, call `GetUtcNow()` (`DECISIONS.md` #009).
9. **One `SaveChangesAsync` per request**, at the end of the service method.
10. **Do not commit secrets.** The Postgres password in `docker-compose.yml`/`appsettings.json` is a
    throwaway local credential and is intentionally committed. Nothing else.
11. **Never run `git commit`, `git push`, or `dotnet ef migrations add` as an agent.** These produce
    permanent artifacts (history, generated migration files) that the human running this exercise owns.
    Prepare the change, explain it, and hand over the exact command.

## Where things go — quick reference

| Adding... | Goes in |
|---|---|
| A rule about one entity's own state | The entity, as a guard clause or method |
| A rule needing a database lookup (existence checks, uniqueness) | Application service, via an explicit
  pre-check that throws `NotFoundException`/`DuplicateKeyException` — the database constraint remains the
  actual guarantee under a race; the pre-check is just for a clean error message |
| A new endpoint | Controller action + application service method |
| A new HTTP-visible failure mode | A case in `TaskFlowExceptionHandler.Map()` |
| Anything that writes | EF Core, via `AppDbContext` directly |

## What to do when uncertain

- If a requirement is ambiguous, **state the ambiguity and the assumption made** rather than picking
  silently.
- If a change touches the status transition rules, the hierarchy rule, or any other business rule with
  real consequences, **draft it, then hand it back for the author to actively rewrite** — not just
  review. That's the standing agreement for this repo; don't silently author these solo.
- If a change would need a new abstraction, propose it with the problem it solves before writing it.
- Prefer the smallest change that is correct.
